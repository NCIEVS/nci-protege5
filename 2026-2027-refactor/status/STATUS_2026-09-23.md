# NCI Protégé Refactor — Status (2026-09-23)

**Goal:** Make the Virtuoso triplestore the lazy, authoritative source of truth for the
Thesaurus, with the OWL API retained only for file input/output. This removes the long-standing
requirement to hold the entire ontology in memory.

## Plan-level status

| Step | Description | Status |
|------|-------------|--------|
| 0–2 | Foundations: branches, OWL↔RDF I/O seam, Virtuoso write-path with revision tracking, per-class commit gate | **Done** |
| 3 | Migrate the demanding consumers (navigation tree, search, classifier, edit path) onto the lazy/Virtuoso model | **Largely complete and working end-to-end at full scale** |
| 4 | Remove the OWL API as the in-memory runtime model and retire the now-dead modules | **Not started** |

The four key architecture decisions (server-synchronized commit as the transaction boundary,
per-class commit gate, append-only change log, and EVS records folded into the commit) are all
implemented.

## What is working now (validated against the full Thesaurus, ~11.4M triples)

- **Fast project creation** — bulk load into Virtuoso at roughly 135K triples/second; loaded
  counts match the established baseline exactly.
- **Lazy project open** — the client opens against Virtuoso without downloading or replaying the
  full ontology.
- **Navigation tree** — responsive. After a series of targeted performance fixes, expanding nodes
  dropped from roughly half a second to tens of milliseconds, even for the densest branches.
- **Class detail / editing panels** — populate on demand directly from Virtuoso.
- **Search** — the Lucene index is built on the server and seeded to the client, then kept current
  incrementally; re-indexing rebuilds from the server.
- **Server-side classification** — classify runs on the server, writes the inferred hierarchy to a
  dedicated graph, and drives both the inferred-hierarchy view and the "discovered subsumptions"
  results panel.
- **Publish / maintenance operations** — server-side squash (history compaction), export-from-server,
  and project delete (which now also cleans up the associated Virtuoso graphs) all function.

## Remaining work

- **Step 4 (the main outstanding effort):** actually retiring the OWL API as the in-memory runtime
  model. The lazy read/write path currently still assembles OWL-API objects internally, and the
  editing, rendering, and commit layers still speak those types. Completing this requires the next
  version of the internal I/O layer. The OWL API file parsers are kept by design.
- **Minor application-level items:** a small number of editing-rule and UI-refresh refinements
  identified during testing; none block the core workflows.
- **Operational robustness:** a few longer-running-operation and recovery improvements to harden the
  system for production use.

## Summary

The lazy read/write backbone (Step 3) is functionally complete and performs at full Thesaurus scale
— navigation, search, classification, publishing, export, and delete all work against the live data.
The next strategic milestone is Step 4: removing the in-memory OWL-API runtime model, alongside the
minor bug cleanup and production-hardening items noted above.

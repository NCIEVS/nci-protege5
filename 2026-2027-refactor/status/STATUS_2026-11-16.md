# NCI Protégé Refactor — Status (2026-11-16)

**Goal:** Make the Virtuoso triplestore the lazy, authoritative source of truth
for the Thesaurus, with the OWL API retained only for file input/output. This
removes the long-standing requirement to hold the entire ontology in memory.

## Plan-level status

| Step | Description | Status |
|------|-------------|--------|
| 0–2 | Foundations: branches, OWL↔RDF I/O seam, Virtuoso write-path with revision tracking, per-class commit gate | **Done** |
| 3 | Migrate the demanding consumers (navigation tree, search, classifier, edit path) onto the lazy/Virtuoso model | **Complete; now validated over the VPN against the real server** |
| 4 | Remove the OWL API as the in-memory runtime model and retire the now-dead modules | **Direction decided; full model replacement deferred by choice** |

The period since the last status (2026-10-26) was focused on one thing:
**making the new architecture usable for editors working remotely over the
VPN.** The 10/26 report had just completed the first clean end-to-end run on a
large ontology on the local/server network; this period took that same system
out to the real remote-editing conditions and made it practical. The four key
architecture decisions are unchanged.

## Progress since 2026-10-26

### Remote project-open is now fast (headline)

On the VPN, opening a project went from **~2 minutes 49 seconds to ~10–12
seconds** — roughly a **15× improvement** — turning remote editing from
painful-to-unusable into practical. This was done as a disciplined
measure → fix → re-measure loop, with every step timed and recorded in a living
performance log so each gain is attributable.

The underlying cause was the same pattern in two different places: over a
high-latency link, the client was fetching information **one item at a time**,
and the per-request round-trip cost — negligible on a local network — stacked up
into minutes. The fixes replace those one-at-a-time bursts with a single batched
request:

- **Building the schema scaffolding on open** was fetching the display label for
  every schema entity individually (~300 separate requests). Fetching them in
  one request cut this step from **~85 seconds to ~3 seconds**.
- **Building the display-name index on open** was doing the same thing for the
  standard vocabulary (built-in terms, Dublin Core, every known data type) —
  about 50 separate requests. Batching them cut this step from **~19.6 seconds
  to under 1 second**. This also appears to have resolved an intermittent
  "wedges on first open, restart to recover" hang, which was the same burst
  of requests occasionally stalling on the VPN.
- **The data-type value-set lists** (the slowest remaining piece) were moved
  **off the open path entirely**, loading in the background after the project is
  already usable. This alone took the schema-load step from ~124 seconds to
  ~5.5 seconds, and the heavy list-walk no longer blocks the editor at all.

Net effect: the editor sees the class tree in about ten seconds, and the
remaining background work completes without holding anything up.

### VPN connectivity and correctness fixes

Two issues that blocked or confused remote use were run down and resolved:

- **A checksum error on open** was traced not to data corruption but to a
  **version mismatch** — the client was running against an older server build.
  Running the current server resolves it; the symptom is now understood rather
  than mysterious.
- **The SPARQL query tab** was pointing at a fixed, built-in endpoint captured
  once when the tab opened, so it silently queried the wrong place after a URL
  change or project switch. It now **follows the active project's triplestore
  automatically** and rebuilds its connection when the target changes, so query
  results always reflect the project the editor is actually in.

### Smoother remote open-from-server experience

- **The project list now appears immediately after login.** Previously, after a
  fresh login the open dialog could come up blank and only populate later (or
  require a second login attempt) — an intermittent annoyance that predated this
  period but was pinned down and fixed here. Measurement confirmed the list
  itself was never slow (it loads in milliseconds); the panel was simply not
  being told to populate at the right moment.
- A related **"resolve inferred view on open"** fix ensures the inferred
  hierarchy is in the correct state right after a project opens.

## Remaining work

- **Further open-time trimming (optional):** the remaining ~10 seconds is now
  mostly the schema load (~6 s) plus baseline project setup and hierarchy
  warm-up. These are candidates for a later pass but are already well within a
  comfortable range for daily use.
- **Rollout and continued validation:** distribute this build to editors and
  keep exercising the large baseline over the VPN under real workloads.
- **Step 4 full model replacement** — still deferred by decision, to be
  revisited once remote/VPN deployment is fully bedded in.
- **Deferred robustness items, unchanged:** making the server's pause state
  survive a restart; a cosmetic refresh notice on the Active Ontology tab that
  clears itself; and the pause-permission model (whether other managers may lift
  a pause), still under consideration.
- The OWL API file parsers are kept by design throughout.

## Summary

Since 2026-10-26 the headline is that **remote editing over the VPN is now
practical**: project open dropped from nearly three minutes to about ten
seconds. The slowness came down to the client fetching information one item at a
time over a high-latency link; replacing those one-at-a-time bursts with single
batched requests — and moving the heaviest remaining work off the open path —
delivered the improvement, and a side effect was clearing an intermittent
first-open hang. Alongside the performance work we resolved the connectivity
confusion (a version-mismatch checksum error) and made the SPARQL tab follow the
active project automatically, and we fixed the long-standing intermittent
empty-project-list-after-login behavior. The project remains on plan, with Step
4's full scope consciously deferred, and the focus now shifts to rolling this
build out to editors and continued real-world validation over the VPN.
